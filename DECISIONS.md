# Решения по реализации

## Реализованный этап

Реализованы все восемь эндпоинтов: создание брони, изменение числа мест, отмена, карточка брони, расписание, загруженность залов, постановка в очередь и выход из неё. Полная карточка кэшируется в Redis с предварительной проверкой версий брони и абонемента в PostgreSQL.

## Контракт и ошибки

HTTP-модели находятся в WebApi, команды и результаты — в BusinessLogicLayer. Ожидаемые отказы возвращаются через `Result<T>`; WebApi преобразует их в `ProblemDetails`. Неизвестные поля запроса игнорируются, числовые поля принимаются как JSON-числа.

При нескольких причинах отказа порядок: отменённое занятие, начавшееся занятие, истёкший абонемент, недостаточная вместимость, недостаток посещений. Формат запроса и ключ проверяются до бизнес-операции.

`createdAt` сохраняется в UTC с точностью до микросекунд: DateTime и PostgreSQL не расходятся при последующем чтении.

## Конкурентность

Занятие, абонемент, бронь и запись очереди используют `Version: uint`, сопоставленный с системным столбцом PostgreSQL `xmin` через `IsRowVersion()`. Токен обновляет сама база при UPDATE; отдельные счётчики version не нужны. Версия занятия читается до суммы активных броней. Метод `MarkForConcurrencyCheck` помечает capacity занятия как изменённую без изменения её значения при изменении мест или состава очереди: это обеспечивает UPDATE занятия с проверкой xmin и защищает общий расчёт. Изменение размера брони соблюдает тот же протокол. Изменения записей вне API также обновляют xmin автоматически.

Каждая попытка — отдельная транзакция ReadCommitted. При конфликте версий откатывается вся попытка, очищается ChangeTracker и заново выполняются все проверки. Всего пять попыток, между ними случайная задержка 20–50 мс с поддержкой отмены. После пяти конфликтов возвращается дополнительный технический ответ `503 ProblemDetails`. Бизнес-отказы не повторяются.

В DAL тот же цикл распознаёт PostgreSQL deadlock `40P01` и нарушение только индекса `UX_waitlist_waiting_user_class` (`23505`). После перечитывания параллельная постановка обнаруживает существующее ожидание и возвращает `already-waiting`. Другие нарушения ограничений не маскируются. Отмена, возврат посещений, выдача новых броней и завершение ожиданий фиксируются одним коммитом; ошибка продвижения откатывает также отмену и возврат.

## Идемпотентность

Область ключа — пользователь и операция. Полная строка сохраняется без ограничения MaxLength; индексируется SHA-256 (32 байта), чтобы размер записи B-tree не ограничивал клиентский ключ. Хеш вычисляется от исходной строки без изменения регистра и усечения пробелов. Отдельную обработку коллизий SHA-256 не реализуем: для ожидаемого объёма данных этот риск принимается.

Уникальный индекс и `INSERT ON CONFLICT DO NOTHING` синхронизируют одинаковые ключи без advisory-блокировок. После вставки выполняется отдельный SELECT, чтобы увидеть завершившегося конкурента. Регистрация ключа и создание брони или ожидания коммитятся вместе; отказ не занимает ключ. До коммита успешная операция заполняет соответствующий FK: `enrollment_id` для брони, `waitlist_entry_id` для очереди. Исходные classId и seats сохраняются отдельно от изменяемых записей.

По согласованной трактовке повтор создания возвращает `201` и текущее состояние связанной брони, включая изменённые seats или status; снимок первоначального ответа не сохраняется. Другие исходные параметры с тем же ключом возвращают дополнительную причину `409 idempotency-key-reused`. Успешные ключи не удаляются по TTL.

Постановка использует отдельную операцию `join-waitlist`. Повтор для ожидающей записи возвращает `201` с текущей позицией, прочитанной вместе с состоянием в одном SQL-запросе. Для завершённого ожидания возвращается дополнительная причина `409 waitlist-inactive`: у него больше нет текущей позиции. Ссылка идемпотентности остаётся на очереди, а ссылка на автоматически выданную бронь хранится у записи очереди. Для новой постановки после завершения нужен новый ключ.

## Очередь и отмена

При постановке абонемент не проверяется и посещения не списываются. Активные брони не мешают ожидать дополнительные места. Заявка сверх полной вместимости отклоняется с дополнительной причиной `409 capacity-exceeded`, чтобы невыполнимая заявка не блокировала очередь.

FIFO определяется `(created_at, id)`. Продвижение синхронно вызывается при отмене или уменьшении брони, а также первом выходе из действующей очереди. Используются все свободные места; запрос первого должен помещаться целиком. Если мест мало, продвижение останавливается до чтения его абонемента. После проверки первого абонементы подходящих по размеру заявок загружаются пакетно; очередь читается порциями по 32 записи с продолжением по `(created_at, id)`, без загрузки всей истории.

Когда мест хватает, истёкший или недостаточный абонемент приводит к `skipped` с причиной `pass-expired` или `pass-exhausted` и временем завершения; затем рассматривается следующий ожидающий. Это обычная ветка бизнес-логики, а не программное исключение. Исключённая запись остаётся в истории и автоматически не возвращается. Подходящий ожидающий получает обычную активную бронь, списание посещений и состояние `promoted`. Обычное создание брони не запрещается из-за наличия очереди.

Выход из `waiting` устанавливает `cancelled` и может продвинуть следующих. Для `cancelled` и `skipped` возвращается `200 cancelled` без изменения истории и повторного продвижения. Для `promoted` возвращается дополнительная причина `409 waitlist-promoted`; выданная бронь сохраняется. После начала или отмены занятия выйти можно, но новые брони из очереди не создаются.

При первой отмене брони `refundedVisits` — количество посещений, начисленных этим вызовом. За два часа и раньше возвращаются все посещения; позднее возврата нет. Для отменённого клубом занятия полный возврат разрешён даже после времени начала. По согласованной трактовке повторная отмена возвращает тот же id, `cancelled` и `refundedVisits: 0`, ничего не начисляя. Историческое значение возврата в БД не хранится. Возврат возможен на истёкший абонемент.

## Карточка и изменение числа мест

Перед чтением кэша короткий SQL-запрос соединяет только бронь и абонемент, проверяет владельца и получает обе версии `xmin`. Чужая бронь и отсутствующая возвращают одинаковый `404` до обращения в Redis; ошибки не кэшируются. Ключ полной карточки — `fitnessclub:{database}:v1:card:{userId}:{enrollmentId}:{enrollmentVersion}:{passVersion}`. Версия занятия в ключ не входит. TTL — пять минут, без продления при чтении.

При промахе один SQL-запрос получает бронь, занятие, зал, абонемент и обе версии. Ключ заполнения строится по версиям именно этого полного запроса, поскольку после предварительной проверки данные могли измениться. Версии остаются внутренними данными DAL и не добавляются в HTTP-ответ. Отменённые занятия читаются с отключённым фильтром.

Ручного сброса кэша в изменяющих операциях нет. Создание, изменение или отмена брони и списания при продвижении очереди автоматически меняют версию брони либо абонемента. Следующий GET использует новый ключ; старые записи удаляются по TTL. Запоздавший GET может заполнить старый ключ, но не перезаписывает карточку с новыми версиями. Изменения занятия и зала вне API могут оставаться в кэше до TTL, как допускает ТЗ.

Ошибки Redis и таймауты при чтении кэша, а также повреждённый JSON трактуются как промах и логируются. Ошибки Redis и таймауты записи логируются без потери свежего ответа из БД. Отмена запроса и ошибки PostgreSQL не маскируются. Rate limit использует Redis с локальным резервным режимом, описанным ниже.

При изменении мест сначала проверяются принадлежность, отмена брони, отмена и начало занятия. Срок абонемента, вместимость и остаток посещений проверяются только при увеличении, в указанном порядке. Уменьшение возвращает всю разницу даже на истёкший абонемент и менее чем за два часа до начала. Равное число мест после проверок состояния возвращает карточку без записи в БД и проверки срока абонемента.

Уменьшение, возврат, продвижение очереди и списания новым броням фиксируются одной транзакцией. Ответ изменения мест читается напрямую из БД после продвижения, без обращения к кэшу и без публикации незавершённой транзакции: если владелец изменяемой брони сам получил места из очереди, возвращается уже окончательный остаток его посещений. Увеличение, как и обычное создание, не запрещается из-за наличия очереди.

## Расписание и аналитика

Расписание использует пагинацию по `(starts_at, id)`: ID разрешает совпадение времени начала. Токен — Base64URL от JSON версии 1 с последней парой и фильтрами `from`, `to`, `roomId`. Повреждённый токен, неизвестная версия и другие фильтры дают `400`; размер страницы между запросами менять можно. Снимок расписания между страницами не фиксируется. Входное время без смещения считается UTC, со смещением приводится к UTC.

Контроллер аналитики принимает обязательные `DateOnly? from/to`, контроллер расписания — обязательные `DateTime? from/to`. Общий `QueryDateModelBinder`, применённый только к этим параметрам, разбирает даты строго как `yyyy-MM-dd`, а моменты времени — как ISO 8601 с приведением к UTC. Отсутствующие, пустые и некорректные значения отклоняются через ModelState и стандартный `400 ProblemDetails` от `[ApiController]`. Swagger описывает параметры как `date` и `date-time`; ручного разбора дат в контроллерах нет.

Фильтрация, сортировка, суммы активных броней и ограничение размера страницы выполняются в БД. Аналитика сначала суммирует активные брони по занятию, затем соединяет их с занятиями и группирует по дате начала в UTC и залу: вместимость и число занятий не умножаются на число броней. Верхняя дата аналитики включена, в отличие от исключённой верхней границы расписания. Отменённые занятия исключены из обеих выборок. Пустые дни и залы в аналитике не создаются. Дополнительных ограничений на длину периода не вводим.

## Лимит запросов и индексы

При доступном Redis общий лимит — 60 запросов пользователя за скользящие 60 секунд. Lua-скрипт Redis атомарно использует время Redis и объединяет счётчик между экземплярами API. Ограничение применяется к помеченным эндпоинтам после аутентификации и до авторизации и привязки модели, включая ошибочные запросы и повторы создания. Внутренние повторы транзакции не расходуют лимит. Вход и health исключены. Пространство ключей разделено по базе PostgreSQL, чтобы тестовая база не влияла на рабочую.

`ResilientUserRateLimiter` при ошибке соединения с Redis или таймауте переключается на `InMemoryFallbackRateLimiter`: общая резервная защита 10 запросов за скользящую секунду, суммарно для всех пользователей и ограничиваемых эндпоинтов одного экземпляра API. Отказы Redis по превышению основного лимита возвращают `429` без обращения к резервному счётчику. Отмена запроса и остальные ошибки, включая ошибки выполнения Redis-команд, не маскируются.

Резервный счётчик и обёртка зарегистрированы как singleton. Под короткой блокировкой одна очередь максимум из 10 отметок времени удаляет запросы возрастом от секунды и учитывает разрешённый запрос. Монотонное время берётся из `TimeProvider`. Словаря пользователей, периодической очистки и фонового процесса нет. В нормальном режиме резервная очередь и её блокировка не используются. В журнал попадают переход на резервный режим и возврат к Redis, а не каждый запрос во время сбоя.

После успешного ответа Redis, в том числе отказа по лимиту, снова используется его общий счётчик. Запросы Redis не расходуют и не сбрасывают резервную квоту. Переноса состояния между Redis и памятью нет; резервная очередь истекает самостоятельно и не сбрасывается при переключениях. Выбранный компромисс ради доступности: при отказе Redis вместо лимита ТЗ на пользователя действует общая резервная защита нагрузки. Она не синхронизируется между экземплярами и теряется при перезапуске процесса.

Подключение создаётся с `AbortOnConnectFail = false`, поэтому отсутствие Redis не блокирует запуск API. `BacklogPolicy.FailFast` не позволяет командам копиться в ожидании восстановления соединения. Существующие таймауты и строки подключения сохранены. При недоступном Redis запросы проходят локальный rate limit, а карточка читается из PostgreSQL в обход кэша.

Для суммы мест используется существующий индекс enrollments(class_id); дополнительный индекс активных броней будет рассмотрен после измерений. Начальные данные и настройки подключения сохранены. Неопубликованная EnrollmentCreation исправлена сразу для xmin, отдельная UseXminConcurrency удалена; локальная база club пересоздана. Миграция WaitlistLifecycle добавляет очередь и её связь с идемпотентностью. Системные xmin миграциями не создаются и не удаляются; таблица очереди изначально пустая.

Миграция ScheduleQueryIndexes добавляет частичные индексы неотменённых занятий по `(starts_at, id)` и `(room_id, starts_at, id)` для расписания с фильтром по залу и без него. Существующий индекс `classes(room_id)` сохранён.
