# Решения по реализации

## Реализованный этап

Реализованы `POST /enrollments`, `POST /enrollments/{id}/cancel`, `POST /enrollments/waitlist` и `POST /enrollments/waitlist/{id}/cancel`. Изменение числа мест, карточка с кэшем, расписание и аналитика будут добавлены следующими этапами. Каркасы сервисов расписания и аналитики уже подключены к DI.

## Контракт и ошибки

HTTP-модели находятся в WebApi, команды и результаты — в BusinessLogicLayer. Ожидаемые отказы возвращаются через `Result<T>`; WebApi преобразует их в `ProblemDetails`. Неизвестные поля запроса игнорируются, числовые поля принимаются как JSON-числа.

При нескольких причинах отказа порядок: отменённое занятие, начавшееся занятие, истёкший абонемент, недостаточная вместимость, недостаток посещений. Формат запроса и ключ проверяются до бизнес-операции.

`createdAt` сохраняется в UTC с точностью до микросекунд: DateTime и PostgreSQL не расходятся при последующем чтении.

## Конкурентность

Занятие, абонемент, бронь и запись очереди используют `Version: uint`, сопоставленный с системным столбцом PostgreSQL `xmin` через `IsRowVersion()`. Токен обновляет сама база при UPDATE; отдельные счётчики version не нужны. Версия занятия читается до суммы активных броней. DAL помечает capacity занятия как изменённую без изменения её значения при изменении мест или состава очереди: это обеспечивает UPDATE занятия с проверкой xmin и защищает общий расчёт. Будущее изменение размера брони должно соблюдать тот же протокол. Изменения записей вне API также обновляют xmin автоматически.

Каждая попытка — отдельная транзакция ReadCommitted. При конфликте версий откатывается вся попытка, очищается ChangeTracker и заново выполняются все проверки. Всего пять попыток, между ними случайная задержка 20–50 мс с поддержкой отмены. После пяти конфликтов возвращается дополнительный технический ответ `503 ProblemDetails`. Бизнес-отказы не повторяются.

В DAL тот же цикл распознаёт PostgreSQL deadlock `40P01` и нарушение только индекса `UX_waitlist_waiting_user_class` (`23505`). После перечитывания параллельная постановка обнаруживает существующее ожидание и возвращает `already-waiting`. Другие нарушения ограничений не маскируются. Отмена, возврат посещений, выдача новых броней и завершение ожиданий фиксируются одним коммитом; ошибка продвижения откатывает также отмену и возврат.

## Идемпотентность

Область ключа — пользователь и операция. Полная строка сохраняется без ограничения MaxLength; индексируется SHA-256 (32 байта), чтобы размер записи B-tree не ограничивал клиентский ключ. Хеш вычисляется от исходной строки без изменения регистра и усечения пробелов. Отдельную обработку коллизий SHA-256 не реализуем: для ожидаемого объёма данных этот риск принимается.

Уникальный индекс и `INSERT ON CONFLICT DO NOTHING` синхронизируют одинаковые ключи без advisory-блокировок. После вставки выполняется отдельный SELECT, чтобы увидеть завершившегося конкурента. Регистрация ключа и создание брони или ожидания коммитятся вместе; отказ не занимает ключ. До коммита успешная операция заполняет соответствующий FK: `enrollment_id` для брони, `waitlist_entry_id` для очереди. Исходные classId и seats сохраняются отдельно от изменяемых записей.

По согласованной трактовке повтор создания возвращает `201` и текущее состояние связанной брони, включая изменённые seats или status; снимок первоначального ответа не сохраняется. Другие исходные параметры с тем же ключом возвращают дополнительную причину `409 idempotency-key-reused`. Успешные ключи не удаляются по TTL.

Постановка использует отдельную операцию `join-waitlist`. Повтор для ожидающей записи возвращает `201` с текущей позицией, прочитанной вместе с состоянием в одном SQL-запросе. Для завершённого ожидания возвращается дополнительная причина `409 waitlist-inactive`: у него больше нет текущей позиции. Ссылка идемпотентности остаётся на очереди, а ссылка на автоматически выданную бронь хранится у записи очереди. Для новой постановки после завершения нужен новый ключ.

## Очередь и отмена

При постановке абонемент не проверяется и посещения не списываются. Активные брони не мешают ожидать дополнительные места. Заявка сверх полной вместимости отклоняется с дополнительной причиной `409 capacity-exceeded`, чтобы невыполнимая заявка не блокировала очередь.

FIFO определяется `(created_at, id)`. Продвижение синхронно вызывается при отмене брони или первом выходе из действующей очереди. Используются все свободные места; запрос первого должен помещаться целиком. Если мест мало, продвижение останавливается до чтения его абонемента. После проверки первого абонементы подходящих по размеру заявок загружаются пакетно; очередь читается порциями по 32 записи с продолжением по `(created_at, id)`, без загрузки всей истории.

Когда мест хватает, истёкший или недостаточный абонемент приводит к `skipped` с причиной `pass-expired` или `pass-exhausted` и временем завершения; затем рассматривается следующий ожидающий. Это обычная ветка бизнес-логики, а не программное исключение. Исключённая запись остаётся в истории и автоматически не возвращается. Подходящий ожидающий получает обычную активную бронь, списание посещений и состояние `promoted`. Обычное создание брони не запрещается из-за наличия очереди.

Выход из `waiting` устанавливает `cancelled` и может продвинуть следующих. Для `cancelled` и `skipped` возвращается `200 cancelled` без изменения истории и повторного продвижения. Для `promoted` возвращается дополнительная причина `409 waitlist-promoted`; выданная бронь сохраняется. После начала или отмены занятия выйти можно, но новые брони из очереди не создаются.

При первой отмене брони `refundedVisits` — количество посещений, начисленных этим вызовом. За два часа и раньше возвращаются все посещения; позднее возврата нет. Для отменённого клубом занятия полный возврат разрешён даже после времени начала. По согласованной трактовке повторная отмена возвращает тот же id, `cancelled` и `refundedVisits: 0`, ничего не начисляя. Историческое значение возврата в БД не хранится. Возврат возможен на истёкший абонемент.

## Лимит запросов и индексы

Общий лимит — 60 запросов пользователя за скользящие 60 секунд. Lua-скрипт Redis атомарно использует время Redis и объединяет счётчик между экземплярами API. Ограничение применяется к помеченным эндпоинтам после аутентификации и до авторизации и привязки модели, включая ошибочные запросы и повторы создания. Внутренние повторы транзакции не расходуют лимит. Вход и health исключены. Пространство ключей разделено по базе PostgreSQL, чтобы тестовая база не влияла на рабочую.

Для суммы мест используется существующий индекс enrollments(class_id); дополнительный индекс активных броней будет рассмотрен после измерений. Начальные данные и настройки подключения сохранены. Неопубликованная EnrollmentCreation исправлена сразу для xmin, отдельная UseXminConcurrency удалена; локальная база club пересоздана. Миграция WaitlistLifecycle добавляет очередь и её связь с идемпотентностью. Системные xmin миграциями не создаются и не удаляются; таблица очереди изначально пустая.
